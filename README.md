## 1. Описание продукта

Модуль предназначен для бесконфликтной координации параллельных расчётов финансовых рисков. Устраняет взаимные блокировки СУБД (Deadlocks), скрытые коллизии скользящих окон дат и затирание промежуточных буферов.

### Ключевые возможности
* **Шлюз приоритета («Люди vs Машина»):** задачи пользователей (`USER`) обладают безусловным приоритетом перед регламентным планировщиком (`MACHINE`). Фоновые задачи откладываются по настраиваемому таймеру (`WAITING_TIMER`) с живым обратным отсчётом и защитой от вечного голодания (`MAX_MACHINE_WAIT_SEC = 90` сек.).
* **Дедупликация с повышением приоритета:** перехват дублей по паре `(Process_ID + Target_Date)` без запуска лишних воркеров с автоматической подпиской на единый `run_id`. Если аналитик запрашивает расчёт, который уже ждёт на таймере от имени `MACHINE`, задача мгновенно повышается до `USER` (`USER_PROMOTION`).
* **Композитный Lock-менеджер:** проверка конфликтов по ключу `(Resource_ID + Date_Range + Access_Mode)` с учётом скользящих окон ($D_{1}^{from} \le D_{2}^{to} \land D_{2}^{from} \le D_{1}^{to}$), точечной блокировкой выходных витрин `mart_*` (`WRITE`) по `target_date` и атомарным резервированием «всё или ничего».
* **Матрица совместимости:** параллельное совместное чтение `READ + READ` без блокировки общих источников (`src_transactions`, `ref_clients`) и параллельный запуск одного процесса за соседние даты (19 и 20 ноября).
* **Изоляция вычислений:** выборка данных в режиме `REPEATABLE READ` (MVCC), персональные буферные таблицы `temp_risk_<run_id>` и финальный атомарный `MERGE` (`INSERT ... ON CONFLICT DO UPDATE`) в витрину `mart_risk_results`.
* **Watchdog с Heartbeat и TTL:** фоновое обнаружение зависших или упавших воркеров по истечении TTL (25 сек.) с автоматическим снятием блокировок и запуском очереди.
* **Live-дашборд и Dry-Run:** предпроверка конфликтов до нажатия кнопки запуска, таймлайн/Гант, карта блокировок, журнал аудита, светлая/тёмная темы и стриминг состояния через WebSocket ($< 1$ сек.).

## 2. Быстрый запуск

### Вариант 1: Запуск одной командой через Docker Compose (рекомендуемый для жюри)

Требуется установленный Docker и Docker Compose.

```bash
docker-compose up --build
```

После старта:
* **Веб-интерфейс дашборда:** [http://localhost:8000](http://localhost:8000) *(если на Windows включён VPN/прокси, открывайте [http://127.0.0.1:8000](http://127.0.0.1:8000))*
* **Интерактивная документация Swagger API:** [http://localhost:8000/docs](http://localhost:8000/docs) *(или [http://127.0.0.1:8000/docs](http://127.0.0.1:8000/docs))*
* **WebSocket поток событий:** `ws://localhost:8000/ws/events`
* База данных **PostgreSQL 16** поднимается автоматически с `healthcheck`, применяет DDL-схему и сидирует **50 клиентов** и **1500 синтетических транзакций**.

---

### Вариант 2: Локальный запуск (браузер или Desktop-окно `pywebview`)

1. Установите базовые зависимости:
```bash
pip install -r requirements.txt
```

2. Убедитесь, что PostgreSQL 16 запущен и доступен по `DATABASE_URL` (по умолчанию `postgresql://postgres:password@localhost:5432/risk_orchestrator`).

3. Запустите веб-сервер напрямую:
```bash
uvicorn backend.main:app --host 127.0.0.1 --port 8000 --reload
```

4. *(Опционально)* Для запуска в виде нативного десктопного окна без браузера доустановите `pywebview` и запустите лаунчер:
```bash
pip install pywebview
python desktop_app.py
```

## 3. Гайд по проверке демо-сценариев для жюри

В левой колонке дашборда ([http://localhost:8000](http://localhost:8000)) расположен блок **«Демо-сценарии для проверки»** — каждый сценарий из кейса запускается в один клик:

| Кнопка / Сценарий в UI | Что запускается | Ожидаемый результат на экране |
| --- | --- | --- |
| **1. «Один процесс за разные даты (19 и 20 ноя)»** | Одновременный запуск `credit_risk` на `2026-11-19` и `2026-11-20` от двух аналитиков | Оба расчёта стартуют **параллельно** (`RUNNING`): источники читаются совместно (`READ + READ`), а витрина `mart_credit_risk` блокируется точечно на свою дату. |
| **2. «Дублирующий запуск (2 аналитика подряд)»** | Одновременный запуск выбранного процесса за одну дату от «Аналитик 1» и «Аналитик 2» | Создаётся ровно **1** воркер (`RUNNING`). Второй аналитик подключается без дополнительной нагрузки и появляется в строке `Подписчики` карточки задачи. |
| **3. «Скрытый конфликт окна (20.11 + 19.11 ETL)»** | `credit_risk` на `2026-11-20` (окно `14.11–20.11`, `READ src_transactions`) и `etl_transactions` на `2026-11-19` (окно `19.11–19.11`, `WRITE src_transactions`) | `etl_transactions` встаёт в блок **«Очередь ожидания»** (`QUEUED`, янтарный бейдж) с указанием конфликтующего ресурса `src_transactions` и стартует автоматически после завершения `credit_risk`. |
| **4. «Регламентный запуск машины (Cron)»** | Запуск задачи от имени `MACHINE` при наличии активных пользовательских расчётов | Задача попадает в блок **«Таймер ожидания машины»** (`WAITING_TIMER`, фиолетовый бейдж `Таймер машины`). После завершения задач `USER` и очередного тика таймера автоматически переходит в работу. |
| **Кнопка «Имитировать сбой (TTL)»** *(на карточке в «Активных расчётах»)* | Chaos-тест отказоустойчивости: остановка `Heartbeat` и имитация зависания воркера | По истечении `lock_ttl_sec` (25 сек.) Watchdog переводит задачу в `FAILED`, снимает её блокировки (`TTL_EXPIRED` в журнале аудита) и запускает ожидающую задачу из очереди. |
| **Живой Dry-Run** *(под формой запуска)* | Смена инициатора (`USER` / `MACHINE`), процесса или целевой даты | Индикатор мгновенно пересчитывает прогноз и список требуемых блокировок: зелёный (`RUN_IMMEDIATELY`), голубой (`DEDUPLICATE`), янтарный (`QUEUE`) или фиолетовый (`WAIT_TIMER`). |

## 4. Запуск автоматических тестов

В проекте реализовано **10 автотестов** (раздел 7 `ARCHITECTURE.md`): 2 модульных теста ядра, 7 интеграционных тестов матрицы совместимости (`TC-01`..`TC-06` + параллельный запуск за соседние даты) и нагрузочный тест на 50 одновременных запросов.

### Запуск внутри Docker-контейнера (рекомендуется)
```bash
# Прогон всех 10 тестов с выводом метрик нагрузочного теста:
docker-compose exec backend python -m pytest -s -v
```

### Локальный запуск
```bash
# 1. Все тесты:
pytest -s -v

# 2. Модульные и интеграционные тесты матрицы совместимости:
pytest tests/test_compatibility.py -v

# 3. Нагрузочный тест на 50 одновременных запросов (< 200 мс, 0% Deadlocks):
pytest tests/test_load_50.py -s -v
```
